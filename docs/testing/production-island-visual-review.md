# 生産の島素材：目視確認と修正対象

2026-10-07、ユーザーがUnityの素材一覧シーンを順に確認した際の指摘を記録する。

## 今後の制作・修正方針

- ユーザー所感：この付近の素材は悪くないが、人間の感覚とずれている印象がある。
- リアリティは求めない。用途や動作が直感的に伝わる、イラストとして自然な表現を優先する。
- 今後の制作・修正ではネット上の関連イラストやゲームのイメージを検索・参照し、形状、配色、構成、動きの参考として用いる。参照元URLと採用した要素を記録する。
- 2026-10-07時点では素材の順次確認を続け、参考画像の収集と素材の修正は未実施だった。

2026-10-08更新：全施設の共通方針を「屋根またはのぼりで用途を即座に識別」「原料→加工→完成品の変化を動きで見せる」「既存ペンギンが作業に関わる」とする。かまぼこ工場の確認後、ユーザーの「今の感じでほかの施設も」に従い14施設と港6段階のv002を制作した。詳細・参考画像・工程・確認方法は [施設デザインv002](../production-island-facilities-v002.md) と [かまぼこ工場v002](../kamaboko-design-v002.md) を参照。新規施設のユーザーによる個別のデザイン確認は未実施。

## VIS-001：乾燥施設の網の形状と動き

- 状態：v002で修正・通常Play Modeで動作確認済み。ユーザーの目視確認待ち。旧v001は比較用として残す。
- 対象：`Assets/3Dmodel/Building_Drying_2x2_v001/Building_Drying_2x2_v001.prefab` の `DryingNet_Anim`。
- 問題：乾燥用の網がベージュ色の板に見える。魚が固定されたまま背面の網だけ上下に動くため、稼働表現が不自然。
- 修正方針案：網目を認識できる形状にし、魚と網の動きに整合性を持たせる。具体的な表現は修正時に検討する。
- v002の変更：板を隙間のある格子の網に変更。加工前・加工後の魚を可動網の子に付け、網の傾きと魚が一緒に動く。屋根はオレンジの魚と骨の模様で干物場を示す。
- 修正素材：`Assets/3Dmodel/Building_Drying_2x2_v002/Building_Drying_2x2_v002.prefab`。工程と子付けは制作時に検証した。要約は動作検証のMarkdownを参照。
- 再確認：正面と斜めから網として認識できること、稼働時に魚と網が不自然に分離して見えないことをユーザーが確認する。

## VIS-002：施設の動きが似すぎる・確認操作が面倒

- 状態：v002を改訂し、通常Play Modeと選択ボタンで検証済み。ユーザーのデザイン確認待ち。
- 指摘：似た動きばかりでは面白さが減る。「次へ」を繰り返さず、好きな施設を簡単に見たい。
- 対応：各施設をネットの一次資料で調査し、回す・引く・刻む・集める・待つ・休むなどの動作、道具、周期を変更。干物は掛けて脇で待ち、海藻はかぎ竿で巻き上げ、電気・水・ガスは残量灯・水位と浮き・弁と圧力針で区別する。
- 確認画面：「施設を選ぶ」から21項目を直接クリック。「全体表示」で同時比較。現在の作業も表示。
- 参照元と全施設の詳細：[施設ごとの特徴と動き](../production-island-facility-motions.md)。
- 検証：15施設×8項目＝120項目PASS。21項目すべての選択ボタン、前後移動、停止・再開、全体・個別、一覧の開閉を確認。仕分けの三方向、残量灯0〜3、水位と浮きの上昇、弁の回転も実フレームで確認した。
- 結果：`ui-verification.txt`、`individual-motion-verification.txt`。

## VIS-003：Game画面のボタンを押しても切り替わらない

- 指摘：ユーザーの実際のクリックでは施設を移動できない。以前の `ui-verification.txt` はクリック処理を直接呼ぶ検査であり、入力経路の検査が不足していた。
- 再現と切り分け：ボタンは有効で位置判定も正常。背面でマウスが無効になる条件を除外して同じ仮想マウスを使い、標準のUI入力経路では切り替わらず、EventSystemとInputSystemUIInputModuleを明示した経路では切り替わった。
- 修正：レビューシーンのFacilityGallery配下にEventSystemとInputSystemUIInputModuleを保存。既存 `Assets/InputSystem_Actions.inputactions` のUI/Point、UI/Click、ナビゲーション等の永続参照を割り当てる。生成処理 `FacilityRevisionBuilder.ConfigureReviewUI` からもこの設定を作り、再生成で失われないようにする。
- 検査：シーンを保存して開き直した後、Input Systemへマウスの移動・押下・解放を送り、通常PlayerLoopからボタンへ届く経路で確認する。SelectやSimulateSingleClickを直接呼ばない。検査の間だけ背面でも入力する設定にし、終了時に元の入力設定へ戻して仮想マウスを削除する。
- 検査対象：前後移動、21施設すべてへの一覧からの移動、一覧の開閉、全体・個別、停止・再開。
- 結果：`ArtSource/ProductionIsland_v002/Facilities/Review/pointer-input-verification.txt`。
- 結果は50操作すべてPASS。21施設への選択、前後移動、一覧の開閉、全体・個別、停止・再開を入力経路から確認した。実機でユーザーが押すマウスの最終確認はユーザー側で行う。
- 上記は制作時の仮想入力検査の記録。現行の回帰検査はUnity Test Frameworkで実行し、実マウスはGame画面で確認する。
- 関連：GameビューのScaleが1.8倍で画面外にはみ出していた状態はMCPで1倍へ戻した。これはEditorの表示設定で、施設の工程やUI配置は変更しない。

### 実マウスの再調査（2026-10-08）

- ユーザーからクリックできないとの再報告。仮想マウス50操作PASSを、実マウスでの解決と同一視しない。
- Unity CLI接続が復帰。正しいレビューシーンで再生中・一時停止なしを確認した。診断時点ではGameのフォーカスがなく、RawInput Mouseは無効で座標が(0,0)だった。この観測だけでは、ユーザーがGameを操作する際の故障原因は確定できない。
- 現在の再生セッションだけ、IgnoreFocusとAllDeviceInputAlwaysGoesToGameViewを有効化してMouseを再有効化し、Gameをフォーカスした。Play終了時に元の設定へ戻す。プロジェクト設定の保存は行わない。
- Game内に「マウス確認」を表示し、PointerDownの到達と選択番号を観測。自動マウス操作を送っていない状態で、PointerDown 3回と選択番号0→1を観測した。ユーザーによる操作成功の回答はまだ得ていない。
- 当時の一時診断コードは公開対象から除外した。マウスの押下数はEditor更新時の観測であり、ゲームフレームとのタイミングによって取りこぼすため、PointerDown到達と施設の切り替わりを優先する。
- Unity CLIのscreenshotは本環境では背景のみを取得した。Game UIの表示成功の証拠としては使用しない。
- 続いてPointerDown 4回、選択番号0→2（施設1→3）まで観測。再生ごとに適用する処理をFacilityDesignGalleryへ追加した。Editorでのレビュー中だけ入力設定の元の値を保持して入力を有効にし、Gameをフォーカスする。OnDisableで元の値へ戻す。実行端末のビルドにはこのEditor専用処理を含めない。
- 最終コード検証：レビュー再生中IgnoreFocus、無効化後ResetAndDisableNonBackgroundDevices／PointersAndKeyboardsRespectGameViewFocusへ復元、再有効化後IgnoreFocus・実Mouse有効・GameViewフォーカスを確認した。設定のコピーを差し替える方法では寿命の問題を検出したため、最終実装は元の値を保持・復元する方法に変更した。確認画面は再生中で残した。
