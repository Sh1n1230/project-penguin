## コンセプト・ゲーム仕様

- **プロジェクト名は Project-Penguin (略称 PP) とする。** (2026-08-30)
- **解決する課題は、CO₂ 排出や地球温暖化に対する当事者意識の不足とする。** 関心が低いからではなく、日々の行動と環境への影響が結びつかず手応えが返らないことが原因だ、という見立てに基づく。 (2026-08-30)
- **想定ユーザーは次の 4 種とする。** 環境問題に関心はあるが自分の生活との関係を具体的に理解できていない人、環境に配慮した生活を始めたいが何から変えればよいか分からない人、環境問題を楽しみながら学びたい学生、学校などで環境問題を学ぶ学生・教育機関。 (2026-08-30)
- **ゲームの骨格は、現実の行動と連動するペンギン育成シミュレーションとする。** ユーザーが何もしないと氷の面積が縮み、ペンギンの住む場所が失われる。損失を避けたいという動機を継続の仕掛けにする。 (2026-08-30)
- **現実の行動の取り込みは、買い物のレシート撮影とする。** レシートの内容を CO₂ 換算でスコア化し、その結果を氷とペンギンの状態に反映する。 (2026-08-30)
- **デイリーミッションを入れる。** 朝にミッションを選び、夜に達成できたかを記録するとボーナスが付く。例はマイボトルの利用や食品ロスの削減。 (2026-08-30)
- **移動手段によるスコアリングは構想に含めるが、スコープアウトしてよい項目とする。** 開発期間が短いため。 (2026-08-30)
- **MVP の完成条件は次の 5 点とする。** (1) ペンギンと氷が表示される、(2) レシートを撮影できる、(3) AI が商品を分類する、(4) Eco Score が計算される、(5) スコアに応じて氷が増減する。 (2026-09-05)
- **MVP の後に足す機能の順序は次のとおりとする。** デイリーミッション、ペンギンの解放、日別グラフ、移動手段、ペンギン図鑑。 (2026-09-05)
- **スコアは絶対量ではなく、過去の自分との比較 (相対値) で評価する。** 生活している限り CO₂ 排出はゼロにならないため、排出の少ない日に加点する形にする。 (2026-09-25)
  - 具体的な計算式は未確定 (「未決・検討中」を参照)。
- **ゲーム仕様は、いったん従来の設計 (レシート、CO₂ 換算、氷とペンギン) のまま作る。** (2026-10-01)
  - 2026-09-29 に、スコアリングの対象を CO₂ から電気・ガス・水道に変える案、放置育成 (インクリメンタル) 型にする案などを議論したが、範囲を広げすぎたとして 2026-10-01 に従来の設計へ戻した。2026-09-29 の個別の合意事項がどこまで残るかは「未決・検討中」に書く。

## 技術構成

- **クライアントは Unity 6 と C# で作る。** React Native + Expo + react-native-filament の構成も比較したうえで、Unity を採用した。 (2026-09-05)
- **Unity Editor のバージョンは 6.6 系 (6000.6.0f1) にそろえる。** 別バージョンで開くとアセットが一斉にアップグレードされるため。 (2026-09-05)
- **UI は UI Toolkit で作る。** (2026-09-05)
- **カメラは WebCamTexture、通信は UnityWebRequest を使う。** (2026-09-05)
- **ゲームの状態は端末上の SQLite に保存する。** 保存先は Application.persistentDataPath とする。 (2026-09-05)
  - 同日の初期案では Supabase (PostgreSQL、Storage) を主なデータ置き場にしていたが、同日中にローカルの SQLite へ変更した。
- **バックエンドは FastAPI とする。** レシート解析 (画像の検証、AI 呼び出し、JSON の検証)、CO₂e の算出 (カテゴリ対応づけ、排出係数、計算)、API キーの管理を受け持つ。 (2026-09-05)
  - 同日の初期案は ASP.NET Core Minimal API、次いで Supabase Edge Functions だった。
- **レシート画像の読み取りには外部の AI (Gemini または OpenRouter 経由のモデル) を使い、商品名・カテゴリ・数量などを JSON にさせる。** CO₂ スコアの最終的な計算は AI にさせず、自前の排出係数テーブルで行う。 (2026-09-05)
- **レシート画像は解析後に破棄し、保存しない。** (2026-09-05)
- **API キーはバックエンドだけが持ち、クライアントには埋め込まない。** (2026-09-05)
- **配布対象は当初 Android とした。** (2026-09-05)
  - その後 iOS も対象に加えた (推定)。2026-09-25 に iOS 実機での動作確認が行われており、README の記載も Android と iOS の両方になっている。
- **サーバーに置くデータは最小限 (数値化した数行程度) にする。** 画像などを置くと費用がかかるため。サーバーの用途は、オンライン同期、ランキング、不正対策のための整合性確認を想定する。 (2026-09-25)
  - サーバーの実装先 (Supabase を使うか) は明示的に確定していない。

## Unity・実装

- **ゲームロジック (氷の減少計算、CO₂e から氷への変換、報酬判定) は UnityEngine に依存しない純粋な C# に分離し、asmdef で区切る。** EditMode テストが書けるようになり、ゲームを起動しなくても AI エージェントがロジックを検証できるため。 (2026-09-05)
- **Unity の MCP サーバーには CoplayDev/unity-mcp を使う。** 接続先はリポジトリで共有する。 (2026-09-05)
- **アプリとしてビルドする設定をリポジトリに入れる。** (2026-09-05)
- **画面の向きは縦に固定する。** モバイル前提のアプリのため。 (2026-09-24、PR #4)
- **バックエンドとの接続前は、スキーマを決めたうえでモックで開発してよい。** (2026-09-14)
- **SQLite とサーバーに保存するデータのスキーマを先に決める。** クライアントが受け持つのは撮影から結果表示までの両端であり、間の処理の仕様が定まらないと実装が進まないため。 (2026-09-25)
- **Hack Day 前の開発は、全体の形を先に作り、計算ロジックはその後に詰める。** (2026-09-25)

## 開発の進め方・GitHub 運用

- **ソースコードは GitHub のリポジトリ project-penguin で管理する。** バックエンドも同じリポジトリに置くため、バックエンドだけを触るメンバーも Unity を入れる。 (2026-09-06)

## JPHACKS2026 への参加

### チームとしての決定

- **Project Penguin で JPHACKS2026 に出る。** (2026-09-03)
  - Project Penguin の企画は、もともと 2026-08-30 に別の学生ハッカソンへの応募用にまとめたものである。
- **参加者は各自がプレエントリーする。** チーム参加でも全員のプレエントリーが必要なため。 (2026-09-04)
- **Hack Day は A 日程 (東京A 会場) で申し込む。** 早い日程を選んだ。 (2026-09-04)
  - 2026-09-30 に東京B 会場とする発言があり、最終的な会場は要確認 (「未決・検討中」を参照)。
- **事前開発と Hack Day の分担は次のとおりとする。** 評価の対象が Hack Day 中に開発した部分に限られるため。 (2026-09-05)
  - 事前に作るもの: 南極の 3D フィールド、ペンギンのモデルとアニメーション、氷の増減、基本 UI、ダミーデータを渡すと世界が変わる状態。
  - Hack Day で作るもの: FastAPI、レシート画像の AI 解析と JSON 化、排出係数による CO₂e 推定、過去平均との比較 (Eco Delta)、SQLite への履歴保存、Unity へ状態を渡す API、デイリーミッションとの連携。
  - Hack Day での優先順位: (1) レシートから商品 JSON、(2) CO₂e 計算、(3) 基準値との比較、(4) SQLite 保存、(5) Unity との連携、(6) 余裕があればデイリーミッション、(7) さらに余裕があれば履歴グラフ。
- **発表では、アイデアだけでなく技術選定の内容も伝える。** (2026-09-25)
- **参加は確定している。** 先着順の受付だったため。 (2026-09-15 に確認)

### チームを制約する JPHACKS の規定

公開 Notion の記載に基づく。日程は変更の可能性があると明記されている。

- **日程** — Learning Day は 2026-10-10 (土) 12:00〜18:00 にオンライン。Hack Day は A 日程 10-17 (土)・18 (日)、B 日程 10-24 (土)・25 (日) で、オフライン参加が必須。Finalist Day (Award Day 進出チームの発表) は 10-30 (金)、Kaizen Sprint (オンラインでの追加開発) は 10-30〜11-14、Award Day は 11-15 (日) に東京大学で開催し、進出チームのみ参加必須。(https://jphacks-info.notion.site/c1e9bc2d28a782ff8fde811a0ea154cc)
- **Hack Day の時間割** — 1 日目は 09:20〜20:20 (Hacking Time 10:20〜19:10、中間発表 19:10〜)。2 日目は 09:30〜19:00 で、**15:00 に Code Freeze**、16:00〜17:00 が Pitch Time。(https://jphacks-info.notion.site/c1e9bc2d28a782ff8fde811a0ea154cc)
- **チーム編成** — チームは 2 名以上。参加確定後は、エントリー時のメールアドレスで JPHACKS の Slack に登録する。(https://jphacks-info.notion.site/c1e9bc2d28a782ff8fde811a0ea154cc)
- **事前開発** — 事前開発や既存物の持ち込みは認められるが、評価の対象は JPHACKS の開発期間内に開発した部分だけである。事前に開発したものを期間中の成果として報告することは禁止。公開されているデータ・ソフトウェア・API・ライブラリは持ち込んで使ってよいが、費用は参加者の負担。(https://jphacks-info.notion.site/df79bc2d28a7823c9b4b81b1ed32bd96)
- **審査での扱い** — 審査基準は「問題着眼点・着想点」「実行・実現可能性」「完成度・動作性」の 3 項目 (各 5 点、Award Day ではプレゼンテーション力を追加)。事前に作った部分をメインの着眼点にすることはできず、「完成度・動作性」は Hack Day 期間中の実装だけを評価する。使用した既存技術そのものは評価の対象外。デモが動くことが最も重視される。(https://jphacks-info.notion.site/f469bc2d28a7834bacf68176ac270d9a)
- **提出方法** — 運営が用意する GitHub の jphacks organization のチームリポジトリを使う。README.md に作品情報とデモ動画のリンクを書く。オンライン審査は Hack Day 終了翌日の月曜 8:00 に始まるため、それまでに push とマージを済ませる。製品情報の提出フォームは Hack Day 2 日目の 15:30 まで (URL は GitHub のみ受け付ける)。(https://jphacks-info.notion.site/27b9bc2d28a7820885b001d5372a95cd)
- **リポジトリの公開** — 提出用リポジトリはパブリックで、MIT ライセンスが置かれる。API キーやトークンなどの秘密情報の扱いに注意すること。プライベートにしたい場合は事務局に相談し、その場合も README はパブリックリポジトリに書く。(https://jphacks-info.notion.site/df79bc2d28a7823c9b4b81b1ed32bd96、https://jphacks-info.notion.site/27b9bc2d28a7820885b001d5372a95cd)
- **発表** — 最終発表は Google Meet で画面録画しながら行い、プロダクトのデモを含める。審査委員は後で録画を見て審査する。(https://jphacks-info.notion.site/52c9bc2d28a783a492d2811809f28b17)
- **情報の公開** — イベントの内容や成果物は公開が前提であり、非公開にしたいアイデアやノウハウは開示しないこととされている。(https://jphacks-info.notion.site/63f9bc2d28a78227a03f814853a2d65a)
- **開発テーマ** — 2026 年のテーマは「X-Tech 2026 〜 Full Stack Hackers 〜」。(https://jphacks-info.notion.site/ae29bc2d28a782b0bd3f815d410e8d69)

## 未決・検討中

- **Hack Day の会場。** 2026-09-04 に東京A で申し込む方針としたが、2026-09-30 に東京B とする発言がある。どちらで確定したかは記録から読み取れない。
- **CO₂ スコアの計算式。** 2026-09-27 に、商品額 × カテゴリ係数で CO₂e を推定し、1,000 円あたりの値を直近最大 5 回の平均と比べる式を実際のレシートで試した。金額で割るため少額の買い物を過大評価する点、ユーザーにとってスコアの上げ方が分かりにくい点が指摘され、手軽さと厳密さのどちらを優先するかも決まっていない。
- **レシート解析に使う AI モデル。** 2026-09-05 に Gemini 3.1 Flash-Lite、OpenRouter 経由の Gemma 4 などが候補に挙がった。2026-09-25 には、レシートだけなら OCR を自作できるのではという案も出た。2026-09-29 には Gemini 3.8 Flash で食事画像から推定する検証が行われた。
- **2026-09-29 に合意した事項の扱い。** 同日、マイナスのスコアリングはしない、ランキングを付けたい (サーバー側の処理として技術的に面白いため)、品目を 1 つずつではなく複数の情報を含む写真で撮らせる、歩いた分をガスの資源量に換算する、エコな行動に加点するパラメータを足す、といった点が合意された。2026-10-01 に従来の設計へ戻したため、これらのうち何を残すかは決まっていない。
- **ランキングの扱い。** 2026-09-29 時点では、レシートを買わずに読み込めてしまうことによる不正への対策と、競争ではなく全員の合計で目標値を目指す協力型にする案が論点として残っている。
- **ゲームの形式。** 2026-09-29 に、放置育成 (インクリメンタル) 型、資源を組み合わせる施設建設、ゲーム内通貨を「お魚」にする案などが出た。2026-10-01 の方針では採用していない。
- **ペンギンの種類とスキン。** 実在する 19 種を候補とする案、帽子をかぶったペンギンなどのスキンやシロクマなど他の動物を加える案、デフォルメしたペンギンをアプリアイコンにする案が出ている (2026-09-29〜30)。
- **複数種のペンギンのアニメーション。** 共通の素体とリグを作ってアニメーションを使い回す方式が提案された (2026-09-04)。手付けのアニメーションは手間が大きいため。採用したかどうかの記録はない。
- **オンライン同期・バックアップに Supabase を使うか。** 2026-09-05 の構成案と 2026-09-25 の議論で前提とされているが、採用を明示した記録はない。
- **スポンサー賞の条件をプロダクトに取り込むか。** 2026-10-01 に提案があった。
